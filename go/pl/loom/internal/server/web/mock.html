The flake is a seed-dependent iteration order in the block builder. Three findings:

  • block_test.go:87 asserts on map iteration order — non-deterministic by design.
  • The builder resets its arena after the first Add, so entry #1 lands in a different slab on ~20% of seeds.
  • CI runs with -count=5, which is why local runs rarely show it.

Fix — sort keys before asserting and reset the arena up front:

func TestBlockRoundTrip(t *testing.T) {
    b := NewBlockBuilder()
    b.Reset() // ← was implicit, seed-dependent
    got := b.Keys()
    slices.Sort(got) // ← was raw map order
    want := []string{"a", "b", "c"}
    if diff := cmp.Diff(want, got); diff != "" {
        t.Fatalf("keys mismatch (-want +got):\n%s", diff)
    }
}

Summary of the SSTable v2 layout

Each table is a sequence of blocks, followed by an index, a bloom partition, and a footer. The invariants:

  • Blocks are snappy-framed, 32 KiB uncompressed target;
  • Restart points every 16 entries — seeks binary-search restarts, then scan;
    • shared prefixes are elided (shared / non_shared / value_len triples);
    • restart array is a trailing u32 run, little-endian;
  • The footer is exactly 48 bytes and ends with the magic 0x8f51_a3c7_22d4_9e01.
Rule of thumb: if you need the bloom filter more than once per 4k keys, your block size is wrong.
type Footer struct {
    IndexHandle   BlockHandle // varint pair
    BloomHandle   BlockHandle
    Padding       [28]byte
    Magic         uint64       // 0x8f51a3c722d49e01
}
